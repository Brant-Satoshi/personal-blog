作者说，和 Claude Code 协作时，他经常想到“地图”和“领土”的差别：提示词、技能和上下文是地图；真正要改动的代码库、现实限制和具体工作环境才是领土。两者之间的差距，就是所谓的“未知”。

![地图与领土](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a4be4919e159adcdfa3ec1c_94358c3c.png)

Claude 遇到未知时，会根据它对用户意图的最佳猜测做决定。任务越长、越复杂，未知就越多。作者认为，Claude Fable 是第一个让他明显感觉“工作质量瓶颈在于我能否澄清未知”的模型。单纯提前规划并不总够用，因为有些未知会在实现深处才暴露，有些甚至会说明你一开始就该换一种解法。

## 认识你的未知

作者把问题拆成四类：

- 已知的已知：你已经能写进提示里的需求和事实。
- 已知的未知：你知道自己还没想明白的部分。
- 未知的已知：你很难提前写清楚，但看到结果时能判断对不对的标准。
- 未知的未知：你完全没意识到的问题、知识缺口或质量标尺。

优秀的 agentic coding 用户往往未知更少。他们知道自己想要什么，也更了解代码库和模型行为。但他们同样会预设未知存在。换句话说，减少未知、并为未知留出处理方式，本身就是使用编程智能体的核心技能。

![未知分类](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a4be4919e159adcdfa3ec52_cc0ee2de.png)

## 帮 Claude 帮你

给 Claude 指令需要平衡：太具体，它可能在更该转向的时候仍死守指令；太模糊，它会按通用最佳实践做假设，而这些假设未必适合你的任务。更有效的方式是告诉 Claude 你当前的思考位置、你对问题和代码库的熟悉程度，并把它当作思考搭档来用。

![帮 Claude 帮你](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a4be4919e159adcdfa3ec55_c4646783.png)

作者把发现未知的方法分成三个阶段。

## 实现前

### 盲点检查

当你进入代码库的新区域，或做自己不熟悉的工作时，最有价值的动作之一是让 Claude 帮你找盲点。可以直接使用“blind spot pass”和“unknown unknowns”这类词，并说明你是谁、你已经知道什么、你不知道什么。

可用的提示思路：

- 我正在给代码库添加新的认证提供方，但不了解这里的认证模块。请做一次盲点检查，帮我找出相关的未知的未知，并告诉我怎样更好地提示你。
- 我不了解视频调色，但需要完成这项工作。请先教我识别调色中的未知未知，这样我才能更准确地给你任务。

### 头脑风暴与原型

有些标准属于“未知的已知”：你说不清，但看到结果就知道喜不喜欢。设计、交互和产品范围常常属于这一类。作者会让 Claude 先探索、头脑风暴或做低成本原型，再决定真正实现什么。

可用的提示思路：

- 我想基于这份数据做一个仪表盘，但不知道有哪些视觉可能性。请做一个 HTML 页面，给我四种差异很大的设计方向。
- 在接入真实逻辑前，先用假数据做一个单文件 HTML 工具栏原型，我想先看布局。
- 这是粗略问题：用户在 onboarding 后流失。请搜索代码库，列出 10 个从低成本到高投入的干预点，我再选择哪些方向值得继续。

### 访谈

头脑风暴之后，通常还会剩下一些模糊处。作者会让 Claude 像采访者一样一次问一个问题，并优先问那些答案会改变架构的问题。

### 参考物

当你描述不出想要什么时，最好给参考。图、文档、截图都可以，但最强参考通常是源码。如果某个库或组件已经实现了你喜欢的行为，就直接把 Claude 指到对应目录，让它读实现细节，即使那是另一种语言。

### 实现计划

准备实现前，作者会让 Claude 写一份实现计划供审阅，并把最可能改变的部分放在前面，例如数据模型、类型接口、用户体验流程。机械性的重构细节可以放在后面。

## 实现中

### 实现笔记

即使计划做得足够好，实现过程中仍会出现未知的未知。作者会要求 Claude Code 维护一个临时的 `implementation-notes.md` 或 HTML 文件，把偏离计划的原因、边界情况和保守选择记录下来，这样下一轮迭代可以从真实经验出发。

## 实现后

### 推介和解释材料

交付不仅是代码完成，还包括让评审者理解并批准。把原型、规格说明和实现笔记整理成一份可发到 Slack 的材料，可以帮助不了解背景的人快速进入上下文，也能让专家看到你已经考虑过常见风险。

### 测验

长会话之后，Claude 可能完成了很多你没意识到的工作。只看 diff 往往不足以理解真实行为，因为很多结果依赖既有代码路径。作者会让 Claude 先生成一份带上下文的变更报告，再在末尾附测验；自己完全答对后才合并。

## 案例：发布 Fable

Fable 发布视频是用 Claude Code 端到端剪辑的。作者本身并不是视频专家，所以他从自己已知的部分开始：Claude 可以用代码剪视频、转录音频，但转录是否够准、能不能用 ffmpeg 精准剪掉停顿或口头填充词，都需要先确认。

随后，他让 Claude 解释 Whisper 之类的转录系统如何工作，又用 Remotion 和转录文本做了一个原型，验证画面 UI 是否能按口播文字计时。最后，视频画面显得有些灰，他知道这和调色有关，却不清楚“好调色”是什么，于是让 Claude 先教他调色知识，帮助他发现自己的未知。

## 地图与领土对齐

模型越强，正确方法带来的杠杆越大。当一个长周期任务结果不对时，问题往往不是“模型完全不行”，而是你还需要花更多时间定义未知，或制定一种允许你和 Claude 在未知中调整路线的实现计划。

解释文档、头脑风暴、访谈、原型和参考物，都是低成本发现未知的方法。越早发现，越不容易在后期付出高昂返工成本。

结论很直接：下一个项目开始时，先让 Claude 帮你找未知。
